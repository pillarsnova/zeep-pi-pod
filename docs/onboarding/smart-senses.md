# ZEEP Smart Senses — การรับรู้หลายเซนเซอร์เพื่อการพัก

สถานะ: **ขอบเขตผลิตภัณฑ์และแผนที่ระบบปัจจุบัน** · ทบทวน 22 กันยายน 2026

## TL;DR

**Smart Senses คือภาพรวม ไม่ใช่ชื่อใหม่ของไมโครโฟน** ระบบเชื่อมเสียง แสง
คุณภาพอากาศ อุณหภูมิและความชื้น กับ HR/RR สถานะเตียง คำสั่งอุปกรณ์ และ
ความเห็นของผู้พัก เพื่ออธิบายเหตุการณ์และเสนอการปรับที่เหมาะกับแต่ละคน
**Smart Ear เป็นโมดูลเสียงภายใน Smart Senses** ชื่อ API, field และ firmware
เดิมยังใช้ได้ ไม่ต้องย้ายข้อมูลหรือเปลี่ยน client

รอบล่าสุดแยกโมดูลการวิเคราะห์และการนำเสนอ โดยคง API และผลลัพธ์เดิม
ไม่เพิ่มเซนเซอร์ ไม่ Flash ไม่เปลี่ยน Sleep State หรือสูตรคะแนน
และไม่เปิดการควบคุมอัตโนมัติ ความสามารถใน source ไม่ได้ยืนยัน
ว่าอุปกรณ์ทุกตัวออนไลน์ ให้ดู Sensor integrity และ provenance ของ Pod จริง

## 1. ขอบเขตห้าด้าน

| ด้าน | สิ่งที่ระบบปัจจุบันรองรับ | สิ่งที่ยังเป็นแผน |
| --- | --- | --- |
| เสียง · Smart Ear | SPH0645LM4H-B: ระดับเสียง, DSP features และป้ายลักษณะเสียงเบื้องต้นสำหรับ Admin | ทดสอบความแม่นยำรายประเภทและเสียงหลายแหล่งพร้อมกัน ไม่ยืนยันแหล่งกำเนิดจากป้ายเพียงอย่างเดียว |
| แสงและการมีอยู่ · Smart Eyes | OPT3001: ความสว่างเป็น lux; สถานะเตียงจาก BCG เป็นข้อมูลประกอบแยกกัน | แสงเชิงสเปกตรัม, ภาพความร้อนความละเอียดต่ำ, radar; lux ไม่ใช่ melanopic EDI และ BCG ไม่ใช่ radar |
| คุณภาพอากาศ · Smart Nose | MH-Z CO₂, PMS PM2.5 และ SGP VOC Index | e-nose/NOx/รูปแบบแก๊สเพิ่มเติม; VOC Index ไม่ระบุสาร กลิ่น หรือผู้สูบบุหรี่ |
| ความสบาย · Smart Skin | SHT3x-DIS วัดอุณหภูมิอากาศและความชื้น เทียบคำตอบความสบายและประวัติของผู้พัก | อุณหภูมิพื้นผิว/ผิวกายและอุปกรณ์อุ่นเท้า; ค่าอากาศไม่ใช่อุณหภูมิร่างกาย |
| การสื่อสาร · Voice | ใช้หน้าจอและปุ่มควบคุมเดิม | คำปลุก คำสั่งเสียง และเสียงตอบกลับ ยังไม่มีระบบรับคำสั่งเสียงภาษาไทยใน runtime นี้ |

HR/RR, Movement และ On/Off-bed จาก LSM-800-T เป็น **บริบทการพักร่วม**
ไม่ใช่ประสาทสัมผัสตัวใหม่ และไม่ได้วัด SpO₂ ความดัน หรือสุขภาพปอดโดยตรง
คำว่า “รองรับ” ในตารางคือเส้นทางโค้ด/contract ไม่ใช่ไฟสถานะการเชื่อมต่อสด

## 2. การทำงานร่วมกัน

1. **รับและตรวจข้อมูล:** ESP/BCG → adapter → canonical sensor fields พร้อม
   เวลา แหล่งที่มา และคุณภาพ; ข้อมูลขาดไม่แทนด้วยศูนย์
2. **วางบนเวลาเดียวกัน:** สภาพแวดล้อม HR/RR สถานะเตียง และคำสั่งอุปกรณ์
   อยู่ใน Adaptive Journey; Admin ดูป้ายเสียงเพิ่มเติมได้
3. **ตรวจสิ่งที่เปลี่ยน:** เปรียบเทียบก่อนคำสั่ง 5 นาที เว้น 1 นาที และหลัง 5 นาที
   แสดงเฉพาะด้านที่ข้อมูลพอ ไม่สรุปว่าอุปกรณ์เป็นสาเหตุจากเวลาที่ใกล้กัน
4. **เรียนรู้ความสบาย:** ใช้ Session ก่อนหน้าที่จบแล้ว โหมดตรงกัน และมีคำตอบ
   จากผู้พัก; 1–2 ครั้งเป็นช่วงเรียนรู้ ตั้งแต่ 3 ครั้งเป็นข้อมูลอ้างอิง
5. **แนะนำครั้งละหนึ่งเรื่อง:** ระบุเหตุผล ผู้ใช้/Admin ยืนยันและปรับผ่านหน้า
   Control เดิม คำตอบรับคำแนะนำไม่ส่งคำสั่งฮาร์ดแวร์เอง

คำแนะนำรุ่นปัจจุบันเป็นกฎที่ตรวจสอบเหตุผลได้ ไม่ใช่โมเดล AI ที่ฝึกจากข้อมูล
หลายเซนเซอร์แล้ว การพัฒนาโมเดลในอนาคตใช้เหตุการณ์และ feedback นี้เป็นหลักฐาน

รายละเอียดช่วงเวลา coverage และสิทธิ์ยึด
[Adaptive Journey](../zeep-adaptive-journey-v1.md) ไม่ทำสูตรคู่ขนานใน Smart Senses
HR/RR ลดลงไม่เท่ากับฟื้นตัวดีขึ้นเสมอ และเหตุการณ์เสียงไม่ยืนยันว่าผู้พักตื่น

## 3. หน้าจอและ API ที่ทีมใช้ต่อได้

| จุดใช้งาน | บทบาท |
| --- | --- |
| Monitor · Smart Senses | สรุปขอบเขตแบบพับเก็บ ไม่ทำสำเนาค่าเซนเซอร์; ดูค่าจริงที่ Sensor integrity/ข้อมูลสด |
| Monitor · Smart Senses / Smart Ear | กราฟเสียง เหตุการณ์และป้ายเบื้องต้นเฉพาะ Admin |
| Monitor และ Sessions · สภาพแวดล้อมระหว่างพัก | Timeline, ก่อน–หลัง, ช่วงความสบาย และคำแนะนำที่เกี่ยวข้องกับรายการนั้น |
| Dashboard / ผลการพัก | ภาษาผู้ใช้ สั้น ชัด; Overnight ใช้ Sleep Score, Nap & Refresh ใช้ Recovery Score |
| Control | ส่งคำสั่งผ่านสิทธิ์และ Safety Policy เดิม ไม่เพิ่มเส้นทางอัตโนมัติ |

ใช้ API เดิม ไม่สร้าง `/smart-senses` ซ้ำกับ domain ที่มีอยู่:

- `GET /api/v1/adaptive/sessions/{session_id}` — ภาพรวมและเหตุการณ์ตามสิทธิ์
- `POST /api/v1/adaptive/sessions/{session_id}/comfort` — ความเห็นเรื่องความสบาย
- `POST /api/v1/adaptive/sessions/{session_id}/decisions` — บันทึกการตอบคำแนะนำ
- `GET /api/v1/admin/acoustics/timeline` — Timeline เสียงเฉพาะ Admin
- `GET /api/v1/admin/contracts/acoustics` — ขอบเขตและสถานะ contract เสียง

Payload และสิทธิ์ใช้ [API/Data/Privacy](api-data-and-privacy.md) และ
[API Schema](../zeep-api-schema-reference-v1.md) ไม่เพิ่มคะแนนชื่อ Smart Senses
ป้าย `snore_like`/`speech_like` ไม่เปลี่ยน State/คะแนน/อุปกรณ์โดยตรง ส่วนค่า
ระดับเสียงที่ใช้ในเกณฑ์สิ่งแวดล้อมและหลักฐานประกอบเดิมยังทำงานตาม policy เดิม

## 4. โครงสร้างสำหรับพัฒนาต่อ

| ส่วน | เจ้าของงาน / จุดเริ่ม |
| --- | --- |
| การรับข้อมูลและคุณภาพ | Firmware/Hardware · `firmware/`, `hardware/`, `sensors/` |
| เสียง | Acoustics/Data · `acoustics/` และ [DSP Plan](smart-ear-dsp-plan.md) |
| เหตุการณ์และข้อมูลอ้างอิง | Pi/Data · `adaptive/`, `sessions/` |
| สิทธิ์และการเชื่อมต่อ App | API · `api/`, [API Schema](../zeep-api-schema-reference-v1.md) |
| การนำเสนอ | UX/Web · `static/partials/app/`, `static/styles/` |
| อุปกรณ์ใหม่ | Hardware/Safety · [BOM](../zeep-sensor-expansion-bom-v1.md) และ [แผน redundancy](../zeep-redundant-sensors-and-device-expansion-v1.md) |

ไม่เพิ่ม package `smart_senses` เพื่อครอบทุกอย่างซ้ำอีกชั้น ชื่อผลิตภัณฑ์รวมได้
แต่ module ยังแบ่งตามหน้าที่ ใช้ contract/device identity เดิม และเพิ่ม field
แบบ backward-compatible เมื่อมีอุปกรณ์จริง

### 4.1 แผนที่โมดูลและจุด Debug

```text
acoustics/
  live_timeline.py          อ่านข้อมูล Session ภายใต้ lock เดิม
  timeline_projection.py   ประกอบผล Timeline; จุดเรียกเดิมยังใช้ได้
  timeline_series.py       สถิติระดับเสียง ย่อกราฟ และรักษาช่วงข้อมูลขาด
  timeline_view.py         จัดเหตุการณ์ ข้อความสถานะ และ metadata
  level_events.py          ตรวจรูปแบบระดับเสียง
  label_events.py          รวมป้าย DSP จาก Firmware

adaptive/
  learning.py              ประกอบผลข้อมูลสดสำหรับ Admin
  features.py              เตรียมค่าจากเซนเซอร์และเทียบข้อมูลอ้างอิง
  learning_quality.py      คุณภาพข้อมูล ความพร้อม Baseline และข้อจำกัด
  learning_recommendations.py  รวมและเรียงคำแนะนำ; ไม่มีสิทธิ์ส่งคำสั่ง
  learning_context.py      ข้อมูล Session สถานะคำสั่ง และที่มาของข้อมูล
  control_policy.py        ยืนยันว่าคำแนะนำต้องรอผู้ใช้/Admin
```

- กราฟขาดช่วงหรือสถิติไม่ตรง: เริ่มที่ `timeline_series.py` แล้วตรวจข้อมูลเข้า
  จาก `live_timeline.py`; ไม่เติมศูนย์เพื่อให้กราฟต่อกัน
- ป้ายเหตุการณ์หรือจำนวนการ์ด: เริ่มที่ `timeline_view.py`; การตรวจพบจริงยังอยู่
  ที่ `level_events.py` / `label_events.py` ไม่เปลี่ยนเกณฑ์ในตัวแสดงผล
- ข้อมูลสด/Baseline ไม่พร้อม: ตรวจ `features.py` และ `learning_quality.py`
- ลำดับคำแนะนำไม่ตรง: ตรวจ `learning_recommendations.py`; สถานะและข้อมูล
  คำสั่งอุปกรณ์ใน `learning_context.py` ไม่ใช่หลักฐานว่าอุปกรณ์ทำงานสำเร็จ

จุดเข้าเดิม `build_acoustic_timeline_snapshot()` และ
`build_adaptive_learning_snapshot()` คงชื่อ signature และ schema เดิม
โมดูลย่อยไม่อ่านฐานข้อมูล ไม่เรียกเครือข่าย และไม่ควบคุมฮาร์ดแวร์
ไม่มี migration หรือ Rerun ผลย้อนหลังสำหรับ Refactor นี้
รายละเอียดผลตรวจ: [Smart Senses Refactor](../reviews/2026-09-22-smart-senses-refactor.md)

ขยายเป็น Smart Senses แล้ว เอกสารนี้สรุปการประยุกต์ ไม่ใช่ผลตรวจ hardware ใหม่

| ประเด็นในต้นทาง | ข้อสรุปสำหรับทีม |
| --- | --- |
| หู ตา จมูก เสียง และผิว | ใช้เป็นกรอบผลิตภัณฑ์ แยกความสามารถปัจจุบันจาก R&D ตามตารางด้านบน |
| ส่วนเสียงบางตอนบอกว่ายังไม่มี class/features | เก่ากว่า source ปัจจุบัน: มี DSP fields และ Admin shadow labels แล้ว ดู [audit 19 ก.ย.](../audits/pi5-esp-system-audit-2026-09-19.md); ยังไม่รับรอง class accuracy |
| ผลจำลอง 5/5 | เป็นตัวอย่างข้อมูลจำลอง ไม่ใช่ความแม่นยำภาคสนาม ไม่ใช้โฆษณาเป็น 100% |
| ควบคุมอุปกรณ์แบบวงปิด | เป็นทิศทางอนาคต ปัจจุบัน recommendation-first และ manual control |
| แสง m-EDI / e-nose / thermal / radar | ยังไม่ใช่ค่าที่อุปกรณ์ปัจจุบันวัดได้ ห้ามเปลี่ยนชื่อ lux/VOC Index/BCG ให้ดูเหมือนมี hardware ใหม่ |
| ASR/TTS ภาษาไทย | ต้องเลือกและทดสอบ engine/โมเดลภาษา ไม่ถือว่าไมค์ตัวเดียวแปลว่าควบคุมเสียงได้แล้ว |
| “ไม่มีกล้อง/ไม่มีภาพ/เสียงไม่ออกจากตู้” | Thermal array เป็นข้อมูลภาพความร้อน ต้องกำหนด retention/สิทธิ์; ระบบเสียงปัจจุบันไม่มี PCM บน Pi ส่วนข้อมูล Wellness มีการ sync ตามสิทธิ์เดิม ไม่ใช้คำรับรองครอบคลุมข้อมูลทุกชนิด |
| ราคาและประสิทธิผลจากงานวิจัย | ใช้ตั้งคำถาม R&D ไม่ใช่ราคา BOM หรือผลของตู้ ZEEP; ตรวจผู้ผลิตและงานฉบับเต็มก่อนลงข้อกำหนด |

รอบนี้ไม่ได้แก้หน้าเว็บไซต์ต้นทางนอก repository จึงเก็บข้อแตกต่างไว้ให้ตรวจสอบ
ไม่คัดลอกข้ออ้างด้านสุขภาพ/ตัวเลขประสิทธิผลที่ยังไม่ได้ตรวจงานฉบับเต็มมาเป็น
ความสามารถของผลิตภัณฑ์

## 6. ลำดับพัฒนาต่อ

1. ใช้ข้อมูลที่มี: Timeline ร่วม ผลก่อน–หลัง ความเห็น และคำแนะนำ พร้อมตรวจ
   ความสด/คุณภาพของแต่ละ sensor; ไม่เพิ่มสำเนาคะแนน
2. เพิ่มหลักฐานทางกายภาพ: ประตู ลมจริง อุณหภูมิพื้นผิว และ sensor สำรองตาม BOM
   เพื่อแยก “ส่งคำสั่งแล้ว” ออกจาก “อุปกรณ์ตอบสนองแล้ว”
3. ทดลอง Smart Eyes/Nose/Skin และ Voice เป็นงานแยก มี device contract,
   งบกำลังไฟ/ประมวลผล privacy และ rollback ของแต่ละชุดก่อนรวม release
4. การควบคุมอัตโนมัติเป็นงานคนละขั้น ต้องมีข้อกำหนดและการอนุมัติชัดเจน
   ไม่เปิดจากการเปลี่ยนชื่อเป็น Smart Senses
