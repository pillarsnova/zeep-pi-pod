# ZEEP Product Language Guideline v1.0

> **สถานะ:** ใช้กับ Dashboard, Control, ประวัติการใช้งาน, รายงาน และ Public API
> **เวอร์ชัน:** `zeep-product-language-v1.0`
> **ขอบเขต:** การนำเสนอข้อความเท่านั้น ไม่เปลี่ยน Sensor, Sleep State, สูตรคะแนน,
> Gate, threshold หรือข้อมูลดิบ

เอกสารฉบับนี้แทนแนวทางข้อความ UI เดิมที่ขัดกันทั้งหมดตั้งแต่วันที่ประกาศใช้
แต่ไม่แทนนโยบายความปลอดภัย ขอบเขตคำกล่าวเชิงสุขภาพ Privacy หรือสัญญา API

## TL;DR

ZEEP สื่อสารกับผู้ใช้ด้วยภาษาที่เข้าใจง่าย ไม่ตัดสินตัวบุคคล และบอกสิ่งที่ทำต่อได้
ส่วนศัพท์วิศวกรรมอยู่ใน Admin โดยเฉพาะ ข้อความด้านความปลอดภัยจริงยังต้องสั้น
ตรง และเด่นชัดเหมือนเดิม

ระบบแบ่งข้อความเป็นสามชั้น:

| ชั้น | ผู้อ่าน | หลักการ |
|---|---|---|
| Product copy | ผู้ใช้ | อบอุ่น กระชับ อธิบายผลและทางเลือกถัดไป |
| Safety copy | ผู้ใช้และทีม | ตรงไปตรงมาเมื่อมีเหตุด้านความปลอดภัยจริง |
| Admin detail | ผู้ดูแล/นักพัฒนา | แสดง reason code, Gate, Coverage, Confidence, Epoch และ provenance ได้เต็ม |

## 1. หลักการเขียนสำหรับผู้ใช้

1. บอกสิ่งที่ระบบทราบก่อน แล้วจึงบอกสิ่งที่ลองทำได้
2. อธิบายผลของ Session ไม่ใช้ภาษาเหมารวมว่าผู้ใช้ “ดี/แย่”
3. ใช้คำว่า “โดยประมาณ”, “แนวโน้ม” หรือ “ช่วงที่พบเป็นประจำของคุณ” ให้ตรง
   กับความสามารถของ Sensor
4. ถ้าข้อมูลยังไม่ครบ ให้บอกว่าระบบกำลังทำอะไร โดยไม่กล่าวโทษผู้ใช้หรืออุปกรณ์
5. แสดงรายละเอียดเทคนิคเมื่อผู้ดูแลต้องตรวจสอบ ไม่วางปะปนในหน้าหลักของผู้ใช้
6. หนึ่งประเด็นสำคัญควรปรากฏเพียงครั้งเดียวในแต่ละหน้า เพื่อลดข้อความซ้ำ
7. เลือกน้ำเสียงจาก “ผู้อ่าน + สถานการณ์ + สิ่งที่ผู้ใช้ทำต่อได้” ไม่ใช้บัญชีคำต้องห้าม
   แบบเหมารวมทั้งระบบ คำตรงอย่าง “ไม่พร้อม” หรือ “ฉุกเฉิน” ยังใช้ได้เมื่อช่วยให้ตัดสินใจ
   ได้ถูกต้อง
8. ภาษาที่นุ่มต้องไม่คลุมเครือ: บอกข้อมูลที่พบ ขอบเขตของการประเมิน และทางเลือกถัดไป
   โดยไม่สร้างคำรับรองทางสุขภาพเกินหลักฐาน

## 2. ตัวอย่างการเลือกคำตามบริบท

ตารางนี้เป็นตัวอย่างสำหรับช่วยให้ทีมเขียนข้อความได้เป็นธรรมชาติ ไม่ใช่รายการคำต้องห้าม
และไม่ใช่กฎแทนคำแบบอัตโนมัติ ผู้เขียนสามารถใช้ถ้อยคำอื่นได้เมื่อสื่อความหมายได้ชัด
จริงใจ และเหมาะกับจังหวะการใช้งานมากกว่า

| บริบท | ข้อความที่อาจฟังแข็งเมื่ออยู่ในหน้าผู้ใช้ | ตัวอย่างที่เป็นมิตรกว่า |
|---|---|---|
| คะแนนต่ำ | `แย่`, `ควรปรับปรุง` | `ให้เวลากับการพักเพิ่ม`, `ยังมีจุดที่ปรับได้` |
| ยังไม่มีคะแนน | `ข้อมูลไม่พอ`, `ไม่ผ่าน Gate` | `กำลังเตรียมผลสรุป` |
| Baseline ยังใหม่ | `ต้องมี 7 Session` | `ระบบกำลังเรียนรู้รูปแบบของคุณ` |
| สภาพแวดล้อม | `แย่`, `วิกฤต` | `ควรปรับ`, `แนะนำให้ปรับตอนนี้` |
| สัญญาณขาดชั่วคราว | `NO DATA`, `Restart hold` | `กำลังเชื่อมต่อข้อมูลล่าสุด` |
| State กำลังเปลี่ยน | `provisional`, `challenger` | `กำลังยืนยันการเปลี่ยนแปลง` |
| ออกจากเตียง | `OFF BED` | `ออกจากเตียง` |
| เวลานอน | `Sensor ประเมินว่าหลับ` | `เวลานอนโดยประมาณ` |
| รูปแบบการหายใจ | `ข้อมูลไม่พอ`, `ควรตรวจซ้ำ` | `กำลังเรียนรู้รูปแบบของคุณ`, `แนะนำให้เช็กอีกครั้ง` |
| ผล Nap | `พักไม่สำเร็จ` | `การพักนิ่งและผ่อนคลายมีคุณค่า แม้ยังไม่หลับ` |

คำอังกฤษและศัพท์ภายใน เช่น `WAIT`, `NO DATA`, `OFF BED`, `provisional`,
`low-confidence`, `Gate`, `Epoch`, `P10–P90`, `BCG coverage` และ reason code
ยังเก็บได้ใน Admin และ Audit แต่ไม่ใช้เป็นหัวข้อหลักในหน้าผู้ใช้

## 3. กฎข้อความที่ยกเลิก

- ยกเลิกกฎห้ามใช้คำเป็นรายคำแบบครอบจักรวาล; ให้พิจารณาตามผู้รับสารและบริบท
- ยกเลิกการบังคับทุกผลให้อยู่ในประโยคสำเร็จรูปเดียวกัน หากข้อความเฉพาะ Session
  ที่เป็นกลางและอธิบายได้ช่วยผู้ใช้ได้มากกว่า
- ยกเลิกการโชว์โครงสร้างอุปกรณ์ (`ESP32`, `GPIO`, `PI5`, ชื่อชิป หรือสถานะ
  Controller) บนหน้าควบคุมของผู้ใช้ โดยยังคงไว้ใน Admin/Debug
- ยกเลิกการใช้คำรุนแรงเป็นป้าย Wellness แบบครอบจักรวาล
- ยกเลิกการส่งข้อความ reason ภายในจากโมเดลไปให้ผู้ใช้โดยตรง
- ยกเลิกการแสดง disclaimer ยาวซ้ำในทุกการ์ด; ใช้หมายเหตุสั้นหนึ่งจุดและเปิด
  รายละเอียดเพิ่มเติมได้
- ยกเลิกการใช้คะแนนเป็นคำรับรองว่า “ร่างกายฟื้นตัวแล้ว” หรือ “พร้อมทั้งวัน”
- ยกเลิกการแสดงการอัปเดตโค้ด, Restart และขั้นตอนยืนยันโมเดลเป็นความผิดปกติของ
  การพัก
- ยกเลิกการตีความ Nap ที่ยังไม่หลับว่าเป็นความล้มเหลว

การยกเลิกเหล่านี้มีผลเฉพาะข้อความนำเสนอ ไม่ยกเลิก quality gate, audit trail,
score eligibility หรือกฎความปลอดภัยภายใน

## 4. กฎที่ยังต้องตรงและชัด

- เหตุประตู, ควัน, CO, CO₂ ถึงเกณฑ์หยุด, อุณหภูมิถึงเกณฑ์ Critical ของ Safety
  Supervisor และ Safe Mode
- การยืนยันลบข้อมูลถาวรหรือจบ Session ของผู้อื่น
- อาการหายใจลำบาก สะดุ้งหายใจ หรือมีผู้สังเกตว่าหยุดหายใจ ซึ่งควรแนะนำให้
  ปรึกษาบุคลากรทางการแพทย์
- ขอบเขตว่า ZEEP เป็น Wellness ไม่ใช่การวินิจฉัย ไม่ได้วัด SpO₂ สมรรถภาพปอด
  หรือความพร้อมทำกิจกรรมทั้งวัน
- การแยก Sleep Score สำหรับ Overnight Recovery และ Recovery Score สำหรับ
  Nap & Refresh
- Privacy, RBAC, API allowlist และข้อห้ามแก้ Raw data

ระดับ `critical` ใน Environment assessment เป็น internal Wellness key เพื่อรักษา
ความเข้ากันได้ของ API ไม่ใช่เหตุฉุกเฉินโดยอัตโนมัติ เสียงเตือนฉุกเฉินต้องมาจาก
Pi-local Safety Supervisor เท่านั้น

## 5. ตัวอย่างข้อความตามสถานการณ์

### Overnight Recovery

> **Sleep Score 78 · ภาพรวมการนอนคืนนี้ดี**
> จุดที่ทำได้ดี: การนอนค่อนข้างต่อเนื่อง
> ลองทำครั้งถัดไป: ลดเสียงรบกวนช่วงก่อนนอน

### Nap & Refresh

> **Recovery Score 74 · ช่วงพักนี้เป็นไปได้ดี**
> คุณได้พักนิ่งตามเป้าหมาย แม้ยังไม่หลับ
> ลองรักษาท่าพักและบรรยากาศที่สบายนี้ไว้

### กำลังสะสมข้อมูล

> **กำลังเตรียมผลสรุป**
> ZEEP กำลังรวบรวมข้อมูลสำหรับการพักครั้งนี้

### รูปแบบการหายใจ

> **จังหวะการหายใจค่อนข้างสม่ำเสมอ**
> อัตราการหายใจโดยประมาณใกล้กับช่วงที่พบเป็นประจำของคุณ
> ข้อมูล Wellness จากช่วงพักครั้งนี้ ไม่ใช่ผลตรวจสมรรถภาพปอดหรือออกซิเจนในเลือด

### เหตุด้านความปลอดภัย

> **ระบบเข้าสู่โหมดปลอดภัย**
> หากกำลังใช้งาน กรุณาหยุดการพัก เปิดประตูออกจาก ZEEP และแจ้งทีมงานทันที

## 6. สัญญา API และการทดสอบ

- Logic ฝั่ง client ต้องอ้างอิง `key` ไม่ใช่ข้อความ `label`
- Public result ส่งเวอร์ชัน `versions.product_language`
- Dashboard, ประวัติการใช้งาน และภาพรายงานผ่าน QR ใช้ Product copy projector
  ชุดเดียวกัน เพื่อไม่ให้ศัพท์ Admin หลุดไปคนละช่องทาง
- Public API แสดงข้อความ Product copy แต่คง stable key, severity และ decision
  สำหรับให้แอปตัดสิน Logic โดยไม่อิงคำแปล
- การเปลี่ยนข้อความไม่เปลี่ยน score, formula version หรือ State timeline
- Regression ต้องยืนยันว่าหน้าผู้ใช้ไม่แสดงศัพท์ภายใน และข้อความ Safety ที่จำเป็น
  ยังอยู่ครบ
- Regression ตรวจเป็นราย surface/role ไม่ค้นหาคำต้องห้ามทั้งไฟล์ เพราะไฟล์เดียวกันมี
  Admin/Debug และข้อความฉุกเฉินที่จำเป็น
- เมื่อ API ได้ key ที่ไม่รู้จัก ต้องใช้ข้อความกลางที่กำหนดไว้ ไม่ส่งข้อความดิบจากข้อมูล
  เก่าหรือปล่อยให้ Client เดาความหมายเอง
- หากคะแนนยังเผยแพร่ไม่ได้ ให้ซ่อนเฉพาะข้อสรุปที่อนุมานจากคะแนน แต่ต้องคงหลักฐาน
  `safety_review`, ค่าที่พบ และเกณฑ์ Safety เพื่อให้ผู้ใช้และทีมดำเนินการได้
- เมื่อ Sensor ที่ Safety Supervisor ต้องใช้ขาดการเชื่อมต่อระหว่างมีผู้ใช้งาน
  ข้อความต้องบอกให้หยุดการพัก ออกจาก ZEEP และแจ้งทีมงาน; ข้อความว่า “พักต่อได้”
  ใช้ได้เฉพาะ Sensor เสริมที่ไม่ใช่ life-safety
- Safety banner ต้องมองเห็นได้ทุกหน้าและใช้ `role=alert`; Admin ต้องได้รับ
  Emergency alert แม้กำลังอยู่หน้า Dashboard หรือ Control และแม้มีคำเตือนอื่นอยู่ก่อน
- ภาพรายงานต้องเรียง `safety_review` ก่อนรายการ Wellness เพื่อไม่ให้คำเตือนถูก
  ตัดออกจากข้อจำกัดจำนวนรายการ
- UI source of truth คือ `static/index.template.html` และ partial ใน
  `static/partials/{control,app}`; สร้าง `static/index.html` ด้วย
  `python ui_composer.py build`
- Coverage และ Confidence แบบตัวเลขคงอยู่ใน Admin/Audit และ structured API;
  หน้าผู้ใช้แสดงคำอธิบายสั้นที่เป็นมิตร แล้วเปิดรายละเอียดเพิ่มได้เมื่อจำเป็น

## 7. เจ้าของข้อความ

Product/UX ดูแลความชัดเจนและโทนภาษา, Sleep/Health reviewer ดูแลขอบเขตคำกล่าว,
Safety owner ดูแลข้อความฉุกเฉิน และ Engineering ดูแล stable key กับ regression
ทุกการแก้ที่เปลี่ยนความหมายเชิงสุขภาพหรือความปลอดภัยต้องผ่านเจ้าของส่วนนั้นก่อน
เผยแพร่
