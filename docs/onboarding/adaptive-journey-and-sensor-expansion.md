## สรุปสำหรับสมาชิกใหม่

งานชุดนี้ทำให้ทีมเห็นว่า ระหว่างพักเกิดอะไรขึ้น ผู้ใช้สั่งอุปกรณ์เมื่อใด
ค่าที่วัดได้เปลี่ยนอย่างไร และช่วงใดตรงกับความสบายที่เจ้าตัวเคยรายงาน
จากนั้นระบบเสนอการปรับครั้งละหนึ่งอย่างพร้อมเหตุผล

รุ่นแรกใช้กฎที่อธิบายได้บน Pi ไม่ใช้ LLM ภายนอก ไม่ฝึกโมเดลออนไลน์
และไม่สั่งอุปกรณ์อัตโนมัติ การรับคำแนะนำเป็นการบันทึกความตั้งใจ แล้วเปิดหน้า
Control ให้เลือกปรับผ่านระบบควบคุมเดิม

ใช้ร่วมกับทั้งสองโหมด โดยไม่เปลี่ยนคะแนนหรือ Sleep State:

| โหมด | คะแนนหลักเดิม | สิ่งที่เพิ่มจากงานนี้ |
| --- | --- | --- |
| Overnight Recovery | Sleep Score | Timeline, ก่อน–หลังปรับอุปกรณ์ และข้อมูลความสบายของการพักค้างคืน |
| Nap & Refresh | Recovery Score | ความสามารถเดียวกัน แต่แยกข้อมูลอ้างอิงตามโหมดและเวลาเป้าหมาย ไม่บังคับว่าต้องหลับ |

## การทำงาน 4 ขั้น

| ขั้น | ระบบทำอะไร | ทีมอ่านผลอย่างไร |
| --- | --- | --- |
| 1. Timeline รวม | อ่านเซนเซอร์ สถานะเตียง เหตุการณ์เสียงที่มีหลักฐาน และคำสั่งที่บันทึกไว้ เรียงบนแกนเวลาเดียวกัน | ใช้หาลำดับเหตุการณ์ ไม่สรุปว่าเหตุการณ์ใกล้กันเป็นสาเหตุของกันและกัน |
| 2. ก่อน–หลัง | เทียบค่าก่อนคำสั่งกับค่าหลังเว้นช่วงตอบสนอง ระบุข้อมูลไม่ครบและคำสั่งซ้อน | ค่าเปลี่ยนไม่เท่ากับผู้ใช้สบายขึ้น; ถ้ามีข้อมูลอ้างอิง จะบอกว่าเข้าใกล้หรือห่างจากช่วงที่เคยสบาย |
| 3. ความสบายรายบุคคล | ผูกคำตอบที่ผู้ใช้เลือกเองกับค่าที่วัดในช่วงนั้น ใช้การพักก่อนหน้าที่จบแล้วและโหมดตรงกัน | ไม่ตอบไม่แปลว่าสบาย ไม่ใช้คะแนนสูงแทนความชอบ และไม่ใช้ความเห็น Admin แทนผู้พัก |
| 4. คำแนะนำหนึ่งข้อ | ตรวจข้อมูลปัจจุบัน ความพร้อมระบบ และความสบายเดิม แล้วเสนออุณหภูมิ เสียง หรือแสงครั้งละหนึ่งด้าน | ผู้ใช้/Admin เลือกรับ คงเดิม หรือไว้ภายหลัง; รับแล้วต้องไปเลือกปรับใน Control อีกครั้ง |

**ช่วงความสบายเริ่มเรียนรู้จากครั้งก่อนหน้าได้** เมื่อมีคำตอบและข้อมูลรองรับ
1–2 ครั้งระบุว่ายังเรียนรู้; ตั้งแต่ 3 ครั้งจึงระบุเป็นข้อมูลอ้างอิงส่วนบุคคล
แยก Overnight และ Nap ตามเวลาเป้าหมาย ไม่ตีความ `auto` ที่ไม่ชัดเจนเป็น Nap

การเปรียบเทียบรุ่นแรกใช้ก่อน 5 นาที เว้น 1 นาที แล้วดูหลัง 5 นาที
ช่วงเวลานี้เป็นค่าเริ่มต้นทางวิศวกรรม ยังต้องทดสอบเวลาตอบสนองจริงของแต่ละอุปกรณ์
ค่าขาดหายไม่แทนด้วยศูนย์ และการลด HR/RR ไม่ถูกสรุปว่าเป็นผลดีโดยอัตโนมัติ

## ผู้ใช้จะเห็นตรงไหน

- **Monitor:** ผู้ดูแลดู Session ปัจจุบัน Timeline ผลก่อน–หลัง และข้อเสนอที่มีข้อมูลพอ
- **Sessions / ประวัติการใช้งาน:** ดูข้อมูลของรายการที่เลือกและให้ความเห็นโดยสมัครใจ
- **คำตอบความสบาย:** สบายพอดี / เย็นเกินไป / ร้อนเกินไป / ไม่ค่อยสบาย
  ระบุว่าจะใช้แนะนำการพักครั้งถัดไป โดยไม่กระทบคะแนน
- **Smart Senses / Smart Ear:** โมดูลเสียงภายใน [ภาพรวมหลายเซนเซอร์](smart-senses.md)
  ป้ายจำแนกเสียงยังเป็นข้อมูลเบื้องต้นสำหรับ Admin ไม่ส่งป้ายหรือ
  feature จำแนกเสียงไปในผลของผู้ใช้ทั่วไป และไม่เก็บ PCM/Raw audio
- **Control:** ยังเป็นหน้าสั่งอุปกรณ์จริงเพียงเส้นทางเดิม ไม่เพิ่มคำสั่งจาก AI โดยอัตโนมัติ

ส่วนใหม่ใช้หัวข้อ “สภาพแวดล้อมระหว่างพัก” แบ่งเป็นข้อมูลอ้างอิง คำแนะนำ และ
ความเห็นของผู้พัก ส่วน Timeline กับรายละเอียดก่อน–หลังเปิดดูเพิ่มเติมได้

รอบปรับ UI 22 ก.ย. ใช้สี ฟอนต์ ไอคอน และปุ่มจากธีมระบบเดียวกันทั้งตัวอย่าง
และ Runtime แสดงบรรยากาศอ้างอิง/คำแนะนำเป็นสองการ์ด ตามด้วยความเห็นแบบข้ามได้
รายละเอียดอยู่ใน [Adaptive Journey — การแสดงผล](../zeep-adaptive-journey-v1.md#การแสดงผลและตัวอย่างจำลอง)

## API สำหรับทีม Backend และ App

Prefix: `/api/v1/adaptive/sessions/{session_id}`

| Method / ส่วนท้าย | ใช้ทำอะไร | ผลสำคัญ |
| --- | --- | --- |
| `GET` | อ่าน Timeline, ก่อน–หลัง, ความสบายอ้างอิง และคำแนะนำ | `journey`, `outcomes`, `comfort_reference`, `recommendation` |
| `POST /comfort` | บันทึกคำตอบโดยสมัครใจ พร้อมอนุญาตใช้ปรับคำแนะนำ | เก็บ evidence แยกจากคะแนน |
| `POST /decisions` | รับ / ปฏิเสธ / เลื่อนไปภายหลัง | `command_executed=false`; ไม่รับคำสั่ง Hardware ใน payload |

ใช้ Browser Auth และ CSRF เดิม User เข้าถึงเฉพาะ Session ของตน Admin เข้าถึงได้
ตามบทบาท ไม่รับ broad API token และไม่ถือ account key ว่างว่าเป็นเจ้าของเดียวกัน
คำตอบสำเร็จใช้ `private, no-store` ส่วน request ที่เขียนข้อมูลต้องมี UUID สำหรับ retry

API นี้เพิ่มจาก Usage Session API ไม่แทน endpoint สรุป Sleep/Recovery Score
ตัวอย่าง JSON, enum, ข้อผิดพลาด และช่วงเวลาที่ใช้คำนวณอยู่ใน
[Adaptive Journey contract](../zeep-adaptive-journey-v1.md)
และ [`api/adaptive_journey.py`](../../api/adaptive_journey.py)
ทีม App ต้องตรวจ OpenAPI ของ release ที่ Deploy จริงก่อนเชื่อมต่อ

## BOM สำหรับต้นแบบและเตรียมผลิต

สถานะ **Engineering candidate / RFQ draft** ยังไม่ใช่รายการสั่งผลิตที่อนุมัติแล้ว

| ชุด | จำนวนตั้งต้นต่อ Pod | เป้าหมาย |
| --- | --- | --- |
| ตรวจตำแหน่งประตู | 2 จุด | แยกเปิดสุด/ปิดสุดจากการส่งคำสั่ง ไม่ใช้แทนอุปกรณ์กันหนีบหรือทางออกฉุกเฉิน |
| วัดลมเข้า–ออก | 2 ชุด | ตรวจลมจริงด้วย sensor + flow element + การสอบเทียบ ไม่แปลงความดันเป็นอัตราลมโดยไม่มีข้อมูลรองรับ |
| อุณหภูมิพื้นผิว | 2 จุด | ตรวจบริเวณเย็นหรือเสี่ยงควบแน่นที่ sensor อากาศเดิมไม่ครอบคลุม |
| Hub และอุปกรณ์ประกอบ | ตามแบบต้นแบบ | วงจรป้องกัน แหล่งจ่าย bus ชุดสาย ขายึด enclosure และอุปกรณ์อ้างอิง |

Candidate ที่ศึกษา: Littelfuse 59140/57140, Sensirion SDP810 และ TI TMP117
รุ่นย่อย ช่วงวัด MCU ราคา ผู้จำหน่าย และจำนวนผลิตยังต้องยืนยัน
ดู datasheet เหตุผลเลือก และข้อจำกัดใน [BOM ฉบับหลัก](../zeep-sensor-expansion-bom-v1.md)
ไม่คัดลอกค่าจัดซื้อมาเก็บซ้ำใน Onboarding

ข้อมูลที่ทีมต้องส่งต่อ: ขนาดท่อและอัตราลมเป้าหมาย รูปแบบ/ช่วงชักประตู จุดติดตั้ง
พื้นผิว ระบบไฟ และจำนวนต้นแบบ/จำนวนผลิต ตัวสำรองต้องมี device ID และตำแหน่ง
แยก ไม่ถือว่า sensor สองตัวอ่านต่างกันแล้วรู้ทันทีว่าตัวใดเสีย

## งานถัดไปและผู้รับผิดชอบตามบทบาท

| ลำดับ | งาน | บทบาทรับผิดชอบ |

จากงานรอบนี้ว่าคำแนะนำช่วยเพิ่มคุณภาพการพักหรือ BOM ผ่านการทดสอบทางกายภาพ
